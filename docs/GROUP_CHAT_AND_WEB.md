# 群聊、执行链与网页版

这份文档记录当前已经定下的产品规则，以及网页版还没做的部分。群聊和执行链已经接进现有调度。Pi 并发队列和容器沙箱只写在这里，代码还没改。

## 群聊

工作流面板可以切到群聊。时间线里能看到执行开始、完成、失败、复核和退回。用 `@节点名` 点名，`@all` 点除开始、结束以外的全部节点。正文里单独出现单词 all 不算点名。没点名的消息只留在群时间线里。

消息按被点名的节点分流：

- 只 `@` 一个空闲节点：直接和这个节点对话。管理员不插在中间。节点自己判断这是提问还是要开始做任务。提问只回复，并留下给之后执行用的指导。要开始做任务，且上游都已完成，才进入调度。
- 这个节点正在执行：不打断正在跑的 Pi。由管理员替它回复。管理员的话只进群时间线，不写成下次执行的指导。
- `@all`，或一次 `@` 多个节点：空闲节点各自回复。管理员只替正在执行的那些节点说一次。这不当成从多个起点启动。
- `@` 人工复核：只记下说明，不跑模型。`@all` 里空闲的复核节点也是这句，不跑模型。

空闲指该节点没有正在跑的任务，也没有进行中的节点对话。待处理、等待上游、已完成、失败、还没执行过，都先直接对话。

## 执行链就是工作流

群聊不另写一套调度。节点确认要开始后，进入现有的那条 Run：同一份依赖、并行规则、验收和人工复核。

从群里点名时，起点是这个节点以及沿出边能到达的下游。画布上的「执行」从开始节点跑整张图。两边看的是同一条 Run 上的同一批任务。

节点做完后，系统用这个节点的身份在群里 `@` 下游，并带上产出短摘要。下一个是谁只看工作流的出边，模型不能改。

- 多个下游写在同一条消息里。它们是否同时跑，由调度看依赖。
- 汇合节点可以先被 `@`，但要等所有上游完成才真正开始。
- 下游是人工复核就停住，等人在面板上决定。
- 没有下游，或下游是结束，这条链收束。

管理员不能启动或重跑工作流，也不能规定谁是下一个。

## A2A

A2A（Agent2Agent）是让不同框架、不同厂商的 Agent 互相委派任务的开放协议，现由 Linux 基金会维护。每个 Agent 公布一张 Agent Card，说明身份、能力和地址。调用方发消息，对方建立一个有状态的 Task，做完后用 Artifact 交回结果。对方不共享内部记忆和工具。

它和现在的两层不是一回事。工作流的边决定谁先谁后。Skill 是 Agent 自己的工具。A2A 是把一件事交给一个外部 Agent 的接口。

A2A 的已完成任务不能重启。Orvia 退回、重跑时要把已完成节点再置为可运行，两套生命周期对不上。管理员如果改成让节点用 A2A 自己发现下一个，就会出现第二套执行顺序。

可以用在边界上：某个节点不是本机 Pi，而是别人部署的 Agent。轮到它时，Orvia 作为 A2A 客户端把上游产物交出去，等 Artifact 写回这个节点的目录，再照旧沿边往下走。整条工作流也可以对外公布一张 Agent Card，外部只看到「这个流程能接一件事」。

## 网页版

MySQL、Redis 和控制台可以放到云上。卡住的是执行方式：每个 Agent 都在 API 那台机器上启动 Pi，产物写在这台机器的 `~/.orvia/workflows`。

公开给别人用时会碰到这些事：

- Pi 以服务器的系统用户运行，Skill 可以执行命令、访问网络、改文件。一个用户能碰到别人的目录。每个租户的执行要放进单独的容器，不能和 API 共用一个系统用户。
- 「这条 Run 正在执行」和「这个节点正在回复」有一部分只记在进程内存里。开两个 API 实例时，同一条 Run 可能被跑两次。发布或重启会掐掉正在跑的 Pi，现有逻辑只把这次收成暂停。按请求扩容的托管不适合。
- 交付物在本机磁盘。容器一换目录就没了。面板里「在访达中打开」是给本机用的，网页版要改成页面里预览和下载。
- 生产环境靠一个 `ORVIA_API_TOKEN`。开发环境可以不登录，默认账号是 `admin@local.orvia` / `orvia-local`。公开使用需要按用户隔离的账号、密钥和配额。预算限额目前不在主流程里。
- 执行进度和群聊回复会把 HTTP 连接一直开到 Pi 结束。负载均衡和 CDN 默认会提前关掉或缓冲这些流。

自己一个人用，可以放在一台固定云主机上：安装 Pi、挂一块持久磁盘、API 只跑一个进程、改掉默认密码和 `WEB_ORIGIN`。访达打开会失效。

做成别人注册就能用的网站，要先有：按用户隔离的执行沙箱、持久且互不可见的文件、真正的账号和配额、以及能跨发布保持的调度。工作流的边和 Run 可以留着。

## Pi 的并发

Pi 不是排队服务。Orvia 每次执行、每次对话都新开一个 `pi` 进程，没有进程池，也没有并发上限。一条工作流里互不依赖的节点会同时启动多个进程。

串行流水线在同一时刻只需要一个正在跑的 Pi。前一个节点的进程退出后，下一个再启动。五个节点前后相连，峰值仍是一个进程。每个节点仍然单独起一次，因为工作目录、模型和 Skill 不同，不把整条链放进一个长寿命进程。

网页版把一条 Run 的执行名额收成 1。画布上的分叉也排成前后脚。侧栏、群聊和管理员与节点执行共用该租户的这一个名额：执行占着时，对话排队，不另开一个 Pi。

上限数的是同一时刻还活着的 Pi 进程。网页请求、排队中的任务、人工复核都不占名额。

两层都要过，更紧的那层先生效：

| 上限 | 含义 | 建议 |
|---|---|---|
| 整机 | 这台机器同时活着的 Pi | 一个进程按 1.5 GB 估，再留 1 GB 给 API。4 GB 内存是 2，8 GB 是 4。不要按 CPU 核数放开 |
| 每个租户 | 这个用户同时活着的 Pi | 公开网页用 1，对应一条串行流水线加它的对话。不能大于整机上限 |

4 GB 内存的机器同时跑 2 个用户，就是整机 2、每个租户 1。本机开发不设这两个数时，保持现在能并行就一起跑的行为。云上必须设整机上限。

满了以后按入队时间等。前面的进程一结束，队头再启动。面板显示前面还有几个人。等了 10 分钟还没轮到，这次任务失败，不再占着连接。

槽位记在 Redis 里，放在真正启动 Pi 的那一处前面。节点执行、侧栏和管理员都走这里。一个槽位对应一个进程；以后换成容器时，一个槽位对应一个容器，队列规则不变。

容器只挂载这一次的工作目录和要用的 Skill，镜像里自带 Pi，模型密钥用这一次的环境变量传入。限制 CPU 和内存。进程结束容器就消失。API 仍负责调度和排队。

这一段队列和容器还没有改代码。一台固定云主机、一个 API 进程，加上队列和容器，是网页版的第一版。要再多开 API 进程时，再把「这条 Run 正在执行」从进程内存改成 Redis 锁的唯一来源。
